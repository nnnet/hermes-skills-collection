# Anti-Patterns

## CRITICAL anti-pattern: SolutionLeakage / SuggestionDuringClarification

**Симптом:** Агент предлагает варианты, гипотезы решения, или таблицы с цифрами ДО того как пользователь окончательно сформулировал цель, критерии и ограничения.

**Почему критично:**
- Якорит мышление пользователя ("ты же сам предложил вариант B")
- Подменяет user-discovery agent-driven recommendation
- Если research/гипотезы прозвучали — назад уже не отыграть, пользователь будет реагировать на них, а не формулировать своё
- Нарушает основной принцип: clarification ≠ ideation

**Триггеры:**
- Любой numbered list of options до `EXIT`
- Таблицы с ROI / ценой / вариантами
- "Кстати, вот что нашёл по теме..." во время ASK или REFLECT

**Жёсткое правило:**
> Во время ASK / REFLECT / HYPOTHESIZE / ACKNOWLEDGE / RESEARCH / ANALYZE_CONTRADICTIONS  агент НЕ предлагает варианты решений и НЕ показывает researched data.
> Research собирается ВНУТРИ агента и используется только для формулировки лучших вопросов.
> Варианты, цифры, прикидки появляются ТОЛЬКО после EXIT и передаются в Phase 1 (chief-manager) или озвучиваются как часть финального Goal-подтверждения.

**Recovery, если нарушил:**
1. Извиниться явно
2. Зафиксировать факт нарушения в `qa_history` и `contradictions.json`
3. Не "отмотать назад" — нельзя; вместо этого зафиксировать что user мог быть заякорен
4. Дальше работать без новых предложений до EXIT

Two layers:
- **Clarification anti-patterns** — failure modes of the PROCESS of eliciting a goal
- **Goal anti-patterns** — failure modes of the RESULTING goal

## Part 1 — Clarification anti-patterns (6)

These are about HOW you talk with the user, not about WHAT you end up with.

### 0. MeansAsGoalAntiPattern (новое, severity критично)

**Симптомы**
- Хотелка формата «<артефакт>, <глагол> <дополнение> <качественно>» (бот-торгующий-крипту-прибыльно, сайт-показывающий-портфолио-удобно, дашборд-собирающий-финансы-понятно).
- Агент СРАЗУ задаёт config-вопросы про предложенный артефакт (биржа? стек? paper или real?), минуя обязательный первый ход — декомпозицию «истинная цель / средство / место».
- В итоге команда строит конфигурацию средства под не подтверждённую трактовку цели — и часто промахивается («сделали бот для крипты», а юзеру нужна была «прибыль» в принципе, готов был на копитрейдинг).

**Почему критично**
- Грамматическая форма хотелки фокусирует средство и прячет истинную цель в наречии («прибыльно», «удобно», «понятно»). Без декомпозиции бот «понимает» хотелку буквально и теряет ось «для чего это вообще».
- Это частный случай `SolutionLeakage`, но более коварный: бот не предлагает СВОЁ решение, он принимает предложенное user'ом средство как заданное.

**Правило**
> Перед любым ASK или REFLECT — декомпозиция и подтверждение, что СРЕДСТВО+МЕСТО действительно выбрано (а не «первое что пришло в голову озвучить»).

**Что делать**
1. Применить шаблон декомпозиции из `SKILL.md` (раздел «ПЕРВЫЙ ход»).
2. Дождаться подтверждения юзера И ответа на вопрос «рамки жёсткие или открыт к альтернативам».
3. Только после этого — переходить к config-вопросам про средство.

**Recovery если нарушил:**
1. Извиниться, признать что начал с конфига без декомпозиции.
2. Сделать декомпозицию задним числом, спросить подтверждение.
3. Дальше — нормальный цикл.

**Реальный кейс 2026-05-24:** на хотелку «Бот, торгующий крипту прибыльно» Гермес сразу спросил «биржа? paper или real?», начал строить бота на Bybit testnet с MA-crossover без подтверждения что прибыль = главная цель и крипта/бот — выбранные оси. Это классический MeansAsGoalAntiPattern.

**Расширение — single-track interpretation:** ещё одна форма MeansAsGoal — бот **мгновенно** выбирает ОДНУ конкретную стратегию реализации (из training data) и больше не исследует пространство решений. На хотелку «прибыльный бот на крипте» сразу прыгает на:

> крипта → automated bot → technical indicators → EMA/RSI на 1h таймфрейме → Bybit

Это лишь ОДНА ветка из десятков возможных: DCA-усреднение, copy-trading, signals-only, portfolio rebalancing, market making, long-hold, arbitrage, grid trading, sentiment-based, options strategies. **Прежде чем фиксировать конкретную стратегию** в декомпозиции — бот должен upewнить себя что осознанно исследовал альтернативы.

**Правило (extension):**
> Перед тем как записать в `Средство` конкретную стратегию (EMA/RSI / Bybit / 1h timeframe / etc.), сделай internal research: какие ЕЩЁ 3-5 альтернативных подходов решают ту же `Истинную цель`? Если из них только одна явно лучше для этого user'а — пиши её. Если нет — оставь `не указано` и спроси user'а какой подход ему ближе. **Не выбирай первый popular pattern из training data.**

**Признак нарушения:** бот пишет специфичные параметры стратегии (EMA9/21, RSI, 1h, BTC/USDT) на turn 1-2 без research-инициативы → MeansAsGoal в single-track форме.

**Расширение — defaults-without-alternatives:** даже когда user говорит «начинай с defaults / делай как считаешь / на твой вкус / уже всё ответил» — бот **НЕ освобождается** от обязанности эксплицитно сравнить минимум 3 принципиально разных подхода (стратегий/стеков/архитектур) и зафиксировать выбор **с обоснованием** ДО chief_spawn.

**Почему это всё ещё MeansAsGoal:** «выбрать default» = выбрать то что чаще всего видел в training, а не то что подходит user'у. User дал боту permission действовать, но не permission **не думать**. Реальный кейс 2026-05-24 (p10 multiturn-005): user сказал «начинай с defaults», бот написал «применяю: Bybit + EMA crossover + Python+ccxt» — без сравнения с DCA / copy-trading / signals-only / grid trading. Это та же ловушка: одна ветка из десятков, взятая потому что popular pattern.

**Правильный паттерн:**

> «Вижу 4 принципиально разных подхода:
> - **A: Trend-following (EMA crossover)** — плюсы: simple, тестируемый; минусы: лагает, плохо на флэте.
> - **B: DCA / усреднение** — плюсы: устойчив к волатильности, мало parameters; минусы: medio-долгосрочный.
> - **C: Copy-trading** — плюсы: ноль кода, моментальный старт; минусы: зависишь от чужого трейдера.
> - **D: Grid trading** — плюсы: работает в range; минусы: ломается на тренде.
>
> Беру A как baseline потому что [конкретное обоснование на основе того что user сказал]. Если предпочитаешь иначе — скажи, иначе погнали с A.»

Это даёт user'у точку входа поправить выбор и фиксирует **осознанный** выбор, а не auto-fill из training popularity.

**Признак нарушения (defaults-вариант):** в финальном bot-turn появляются конкретные инструменты/параметры (Bybit, EMA9/21, Python+ccxt) **без** предшествующего разбора альтернатив с trade-offs → defaults-without-alternatives → MeansAsGoal.

### 0c. WithinSessionSelfCitation (новое, severity критично)

**Симптомы**
- На turn N бот сам перечислил варианты в ответ на explicit user-вопрос («какие есть биржи?» → «Binance, Bybit, OKX, …»).
- На turn N+1 бот **подбирает один из этих вариантов** (часто первый) и записывает его в декомпозицию слот как **факт о user'е**: «**Средство**: бот на Bybit с EMA/RSI стратегией».
- Свой собственный предыдущий output стал «известным контекстом» для следующего хода.

**Почему критично**
- User **не выбирал** Bybit, не подтверждал EMA/RSI. Бот сам себя процитировал и принял свою цитату за подтверждённый факт.
- Это контаминация декомпозиции через bot's own output — даже более тонкая чем `EmptySlotFillFromTraining`, потому что выглядит «обоснованно» (бот может сослаться на «вы это обсуждали»).
- В реальности бот предлагал список — user не сделал выбор. Дефолтный выбор первого = MeansAsGoalAntiPattern.

**Правило**
> Свой OWN-предыдущий output **не становится фактом** в декомпозиции. Только то что user **literally сказал** идёт в слоты. Если бот предложил список — для декомпозиции user должен **явно выбрать**.

**Реальный кейс 2026-05-24 (p10 multiturn-004):**
- turn 2: user спросил «exchange: а какие у тебя варианты?» → бот ответил «Binance, Bybit, OKX, Bitget, KuCoin».
- turn 3: бот записал «**Средство**: торговый бот (у тебя уже есть на Bybit, EMA9/21+RSI, BTC/USDT 1h)».
- User об этом ни единого слова не говорил. Bybit взят первым из бот's собственного списка; EMA/RSI и BTC/USDT — из training data popular pattern; «уже есть» — придумано целиком.

**Recovery если нарушил**
1. В декомпозиции заменить self-cited варианты на `не указано` или ровно слова user'а.
2. Если хочется зафиксировать выбор — задать explicit вопрос «Из перечисленных — выбираешь X?»

**Маркеры в outgoing**
- «у тебя уже есть <бренд>» — где бренд был в твоём списке варианты выше
- «выбрали <X>» / «настроено на <X>» — без явного user-выбора
- любая конкретика про user'а которая взялась из твоего OWN-message а не user-message

### 0d. NonAnswerInterpretedAsAnswer (новое, severity критично, ОБЩЕЕ правило)

**Симптомы**
- Бот задал конкретный вопрос («зачем тебе это?», «какой бюджет?», «paper или real?»).
- User ответил **не по существу** — про другое, неоднозначно, surface-affirmation, перевод темы, уклонение от конкретики.
- Бот **интерпретировал** non-answer как валидный ответ: «ты ответил X — это значит Y, правильно?», и пошёл дальше с **самостоятельно сконструированным** content'ом в слотах.

**Почему критично**
- Декомпозиция строится на догадке бота, не на словах user'а. На следующих turn'ах user обнаруживает что бот «понял» не то — но цикл прояснения уже зашёл слишком далеко чтобы откатываться.
- Это применимо КО ВСЕМ типам вопросов, не только мотивационным. Любой слот — цель/средство/место/мотивация/срок/бюджет/команда/рамки — подвержен этой ловушке.

**Правило (общее)**
> ЛЮБОЙ ответ user'а, не являющийся прямым ответом на конкретный заданный вопрос — это **non-answer**. Единственный правильный ход — переспросить (можно перефразировать), НЕ интерпретировать. Не строить декомпозицию на догадке «он наверное имел в виду…».

**Паттерны non-answer (распознавать как такие):**

| Паттерн | Пример | Как распознать |
|---|---|---|
| Отвечает про другое | Q: «зачем тебе это?» A: «хочу чтобы работало и развивалось» | Ответ про средство, не про мотивацию |
| Перевод темы | «начинай с defaults», «делай как считаешь», «продолжай», «уже всё ответил» | Призыв к действию вместо ответа |
| Уклонение от конкретики | «небольшой, не хочу пока называть» (про бюджет) | Явный отказ дать ответ |
| Молчание / пропуск | User ответил на 2 из 3 вопросов | Часть вопросов осталась без ответа |
| Surface-affirmation | Q: «зачем тебе это?» A: «ок» / «угу» / «да» | Yes/no-форма на open-ended вопрос |
| Тавтология | Q: «что для тебя успех?» A: «когда всё успешно» | Содержит сам вопрос как ответ |

**Что делать**
1. Распознать non-answer ДО того как сформировать следующий REFLECT.
2. Переспросить вопрос — можно перефразировать, можно дать категории-варианты (НЕ бренды, см. `BrandListInClarificationQuestion`):
   > «А если по-другому — это финансовая независимость? любопытство? давление обстоятельств?»
3. Соответствующий слот остаётся `**не указано**` пока user не ответит по существу.
4. НЕ продолжать в режиме «ну ок, я понял что ты имел в виду X».

**Recovery если нарушил**
1. На следующем turn'е — извиниться, признать что приписал user'у то, что он не говорил.
2. Откатить соответствующий слот в декомпозиции в `**не указано**`.
3. Переспросить вопрос по существу.

**Реальный кейс 2026-05-24 (p10 multiturn-005):**
- turn 1: бот спросил «зачем тебе это? финансовая независимость, дополнительный доход, эксперимент, или что-то другое?»
- turn 2 user: «хочу чтобы работало и развивалось» (про БОТА, не про мотивацию)
- turn 2 бот: «ты ответил «хочу чтобы работало и развивалось». Это про долгосрочный рост, правильно?» — **интерпретировал non-answer как «долгосрочный рост»**, не дождался подтверждения, поехал дальше.
- В итоге `Истинная цель` зафиксирована как «прибыль с крипторынка» — на основе бот's догадки.

**Маркеры нарушения в outgoing:**
- «ты ответил X — это значит Y, правильно?» (бот сам построил Y)
- «понял, тогда…» после non-answer
- «учитывая что ты сказал…» когда user сказал не то что бот процитировал

### 0a. EmptySlotFillFromTraining (новое, severity критично)

**Симптомы**
- Декомпозиция формально показана, но пустые слоты («Средство», «Место/контекст», состояние артефакта) **дозаполнены из training data** под видом «как услышал».
- Появляются конкретные числа, инструменты, биржи, версии стека, состояние готовности — которых пользователь не озвучивал.
- Формулировки-маркеры: «Уже есть: <…>», «Бэктест <число>%», «По умолчанию <инструмент>», «Скорее всего <…>», «Типично используют <…>», «Paper trading сейчас, реал — потом».
- Юзер либо принимает фантазию за свою (теряется true goal), либо тратит раунд на «нет, я этого не говорил».

**Почему критично**
- Это NOT факт-чекинг через тулы — это LLM-projection из general knowledge о доменной области, выданное как «я тебя понял».
- Контаминирует подтверждение: юзер кивает на декомпозицию → бот считает что «средство = Bybit testnet с EMA/RSI» подтверждено → команда строит конкретный артефакт под выдуманную спецификацию.
- Отличается от `MeansAsGoalAntiPattern`: там бот СРАЗУ идёт в config-вопросы; здесь — корректно открывает skill, корректно делает декомпозицию, но в момент написания слотов «затягивает» детали из training data.
- Опаснее `SolutionLeakage`: solution leakage предлагает решения user'у; здесь бот ПРИПИСЫВАЕТ user'у уже принятые решения, которых тот не делал.

**Правило**
> ЛЮБОЙ слот в декомпозиции, который пользователь явно не озвучил в этой сессии — пишется как `**не указано**` без продолжения. Никаких «вероятно», «уже есть», «обычно». Если хочется добавить деталь — это всегда сигнал tighteneren из training data.

**Что делать**
1. Перечитай слот: если строка содержит существительные/числа/инструменты, которых нет в исходном сообщении user'а — это фабрикация. Замени на «не указано».
2. Если деталь нужна для следующего шага — спроси её **отдельным вопросом** ПОСЛЕ подтверждения декомпозиции, не вписывай в саму декомпозицию.
3. Research допустим (см. `SKILL.md` §«Что МОЖНО»), но его результат остаётся в твоей голове до EXIT — в чат он не уходит.

**Recovery если нарушил:**
1. Извиниться, признать что дофабриковал слот.
2. Переписать декомпозицию с теми же словами что user реально сказал + явные «не указано» в пустых слотах.
3. Спросить подтверждение снова.

**Маркеры в outgoing message (если видишь у себя — стоп, перепиши):**
- «уже есть <артефакт>»
- «бэктест <число>»
- «скорее всего <…>»
- «обычно <…> / типично <…>»
- «по умолчанию <инструмент>»
- любые конкретные тикеры/биржи/фреймворки/числа, которых не было в user message

**Реальный кейс 2026-05-24:** на хотелку «Бот, торгующий крипту прибыльно» Гермес корректно вызвал `skill_view(orientation/desire-to-goal)`, корректно построил структуру декомпозиции, но в слот `Средство` дофабриковал: «торговый бот. Уже есть: Bybit, BTC/USDT, бэктест +29% за 6 мес», в `Место` дофабриковал: «Paper trading сейчас, реал — потом». Юзер ни единого из этих слов не произносил. F1 gate сработал, skill_view сработал — фабрикация всё равно прошла на уровне токенов в outgoing message, минуя любые тул-ворота. Единственная защита — explicit правило в самом скиле + маркеры для самопроверки.

### 0b. BrandListInClarificationQuestion (новое, severity критично)

**Симптомы**
- Декомпозиция в целом корректная, пустые слоты помечены `не указано`.
- НО в финальном вопросе про рамки или в любом уточняющем вопросе бот **перечисляет конкретные бренды / продукты / платформы / фреймворки** в скобках или как примеры.
- Пример: «есть уже какие-то устройства (Philips Hue, Home Assistant, Яндекс, Apple Home и т.д.)»
- Пример: «где ищешь работу (hh.ru, LinkedIn, …)»
- Пример: «какой стек (Notion, Google Sheets, Airtable, …)»

**Почему критично**
- Это мягкая форма `SolutionLeakage`. Пользователь видит готовый список и переходит в режим «выбрать из вариантов», вместо того чтобы сказать своими словами.
- Пользователь, не назвавший бренд САМ, теперь либо называет один из показанных (anchored to your list), либо говорит «ничего такого нет» (anchored к категории, которую ты задал).
- Истинная цель и средство могут лежать совсем в другой плоскости (например, для «автоматизируй дом» — реальная цель «меньше тратить времени на свет утром», и решение = простой таймер на $5, а не Home Assistant).
- В отличие от `EmptySlotFillFromTraining` — там бот ПРИПИСЫВАЕТ user'у факты; здесь бот ПРЕДЛАГАЕТ user'у варианты. Обе формы контаминируют прояснение, но эта чуть менее очевидная и поэтому опаснее.

**Правило**
> В любом вопросе во время прояснения — спрашивай **категорийно**, не **списком брендов**. «Есть уже какие-то устройства / платформа?» — нормально. «(Philips Hue, Home Assistant, Яндекс, Apple Home)» в скобках — нельзя.

**Исключение** — user **сам явно попросил** список вариантов («а какие есть?», «дай список», «что посоветуешь из...?»). В этом случае короткий ответ списком (3-5 известных опций) допустим. После — вернуться к уточнению цели; не углубляться в config-вопросы про каждый из перечисленных.

**Что делать**
1. Если хочется уточнить «что уже есть» — формулируй открыто: «Есть ли уже какие-то устройства / платформа / решение, которое работает сейчас?»
2. НЕ называй конкретные имена САМ. Если user не знает категории — он спросит, тогда можно дать 1-2 примера. До этого — категория без брендов.
3. Если user сам назвал бренд — можно подтвердить ровно его слова, не дополнять списком альтернатив.
4. Если user явно попросил список — дай его коротко (3-5 пунктов), потом продолжи прояснение.

**Recovery если нарушил:**
1. Признать: «Извини, я предложил список вариантов — это анкорит. Спрошу проще.»
2. Переформулировать вопрос без брендов.

**Маркеры в outgoing (если видишь у себя — стоп, перепиши):**
- открывающая скобка `(` после категорийного слова + список через запятую с заглавными буквами (бренды)
- «(например, …)» с конкретными именами брендов
- «(N, M, K и т.д.)» с конкретными продуктами

**Реальный кейс 2026-05-24:** на хотелку «Автоматизируй мой дом» Гермес сделал корректную декомпозицию (3 слота `не указано`, без фабрикации), но в вопросе про рамки спросил: «есть уже какие-то устройства / платформа (Philips Hue, Home Assistant, Яндекс, Apple Home и т.д.) — или начинаем с чистого листа?». Пользователь зафиксировал FAIL, и эта подсказка четырёх брендов в скобках — единственная причина.

### 1. Допрос вместо прояснения

**Симптомы**
- Жёсткий список обязательных вопросов
- if-else: "ответили на это, теперь следующий"
- Ощущение экзамена у пользователя

**Почему плохо**
Пользователь начинает подбирать «правильные» ответы, фантазировать, защищаться. Достоверность падает.

**Правило**
> Чем жёстче форма — тем лживее содержание.

**Что делать**
Открытые вопросы. Не более 3 за раунд. Слушать тон ответов, не только содержание.

### 2. Линейная воронка истины

**Симптомы**
- "desire → goal → metrics → done" как однонаправленный конвейер
- Запечатывание плохо сформулированной цели до того как пользователь сам её понял

**Правило**
Цель часто становится ясной *в процессе*, не до. Возврат — нормально.

**Что делать**
Использовать REFLECT action когда пользователь сам не уверен. Goal-drift в первых итерациях не катастрофа, а норма. Аномалия — когда goal-drift продолжается на итерации 4-5.

### 3. Фетиш полноты

**Симптомы**
- "Пока не соберём всё — не идём дальше"
- Тревожность по поводу пустых primitive
- Бесконечный цикл уточнений

**Правило**
Полнота — иллюзия. В сложных задачах всегда есть скрытые ограничения и неосознаваемые мотивы.

**Что делать**
Выход по sufficient (confidence ≥ 0.7 + stability ≥ 0.7), не по completeness. Acknowledged contradiction — валидный финал.

### 4. Противоречие = ошибка

**Симптомы**
- Попытка "убрать" противоречия в данных
- Принуждение пользователя выбрать одну сторону

**Правило**
Противоречия — сигналы. Часто указывают на скрытые цели, конфликт ролей, разные контексты.

**Что делать**
`add_contradiction()` — фиксировать. `resolve_contradiction(status="acknowledged")` — оставлять открытым валидно. Эксплуатировать как информацию, не подавлять.

### 5. Человек = источник истины

**Самый важный.**

**Реальность**
- Человек не наблюдает себя полностью
- Рационализирует задним числом
- Путает желания и социально одобряемые формулировки

**Правило**
> Истина — не в словах человека, а в **динамике его ответов**.

**Что делать**
Tracking `goal_versions` — если формулировка стабилизировалась за 2-3 итерации, можно доверять. Tracking `behavior_stability` — если пользователь начинает подтверждать вместо изобретать новых аспектов, готов к выходу.

## Part 2 — Goal anti-patterns (8)

These are checks on the FINAL Goal object before handing off to chief-manager. Implemented in `detect_anti_patterns(state)`.

### 1. GoalWithoutCriteria

**Условие**: `goal_statement` есть, `success_criteria == []`

**Severity**: 0.8

**Fix**: ASK action с фокусом на критерии. "Как именно мы поймём что готово?"

### 2. NonMeasurableGoal

**Условие**: `goal_statement` есть, `metrics == []`

**Severity**: 0.7

**Fix**: ASK action с фокусом на метрики. "Чем будем мерить эти критерии?"

### 3. GoalWithoutOwner

**Условие**: `goal_statement` есть, `subject == {}`

**Severity**: 0.6

**Fix**: ASK о ролях и ресурсах. "Кто это делает? С какими ресурсами?"

### 4. CriteriaWithoutGoal

**Условие**: `success_criteria != []`, `goal_statement is None`

**Severity**: 0.9

**Fix**: REFLECT — критерии есть, надо извлечь цель которой они служат.

### 5. MetricsWithoutGoal

**Условие**: `metrics != []`, `goal_statement is None`

**Severity**: 0.9

**Fix**: REFLECT — метрики без цели = optimizing proxy without knowing what.

### 6. HypothesisWithoutContext

**Условие**: `hypotheses != []`, `context == {}`

**Severity**: 0.5

**Fix**: ASK о контексте — гипотезу не на чем проверять.

### 7. GoalDrift

**Условие**: `len(goal_versions) >= 2` и `jaccard(versions[0], versions[-1]) < 0.2` и `iteration < 4`

**Severity**: 0.5

**Fix**: REFLECT с признанием — "цель сильно изменилась с начала, давайте зафиксируем".

### 8. UnstableGoalDefinition (post-soft-cap)

**Условие**: `iteration >= 5` и `stability_score < 0.5`

**Severity**: 0.7

**Fix**: REFLECT + спросить пользователя — продолжить или зафиксировать как есть с пометкой "low confidence".

## When the validator fires

Run `detect_anti_patterns(state)` on every iteration (it's cheap). Add the result to the `next_step()` instruction packet so the agent's next question can address the issue directly.

Anti-patterns of severity ≥ 0.8 should block EXIT — controller logic doesn't currently enforce this, but the agent should add a check before calling `build_goal_for_chief_manager()`.

## Production tip

If the same anti-pattern fires 3+ iterations in a row, the agent is stuck in a local minimum. Surface this to the user: "Я уже 3 итерации спрашиваю про X, но мы не движемся. Может я задаю не тот вопрос?"
